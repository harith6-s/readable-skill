# Readable

frontmatter (ใช้เหมือนฉบับอังกฤษ):
- **description:** ใช้เมื่อโค้ด Python ที่ทำงานได้อยู่แล้วไล่อ่านยาก เพราะคนอ่านต้องกระโดดไปกลับระหว่างฟังก์ชันหรือไฟล์ (ในไฟล์เดียวกันหรือข้ามไฟล์) เพื่อตาม request, job หรือ task หนึ่งตัวตั้งแต่ต้นจนจบ, เมื่อไม่มีใครบอกได้ว่าฟังก์ชันไหนคือจุดเริ่มหรือ payload ถูกประกอบที่ไหน, เมื่อการ refactor "ให้อ่านง่าย" รอบก่อนทำให้โค้ดแตกเป็นชิ้นเล็กลง หรือเมื่อ feature ใหม่ต้องอ่านจากบนลงล่างได้ตั้งแต่แรก
- **disable-model-invocation:** true (ไม่ทำงานเอง ต้องเรียก `/readable` ทุกครั้ง)
- **argument-hint:** `mode=new|refactor|migrate <target> [apply=v2|replace] [out=<path>] [work=<folder>] [layout=A|B|AB] [depth=1-3] [style=auto|function|class]`
- **metadata.version:** 1.1

## ภาพรวม

request หรือ task หนึ่งตัวต้อง**อ่านจากบนลงล่างจบในที่เดียว** ความอ่านง่ายวัดกันที่**จำนวนชั้นของการกระโดด** ไม่ใช่จำนวนบรรทัด ไฟล์ยาวขึ้นหรือโค้ดช้าลงเล็กน้อยรับได้ แต่**พฤติกรรมเปลี่ยนไม่ได้**

skill นี้คือ**กระบวนการที่มี gate** ไม่ใช่รายการคำแนะนำ ทุกขั้นจบด้วยหลักฐาน (ไฟล์หรือผลของคำสั่ง) ห้ามเริ่มขั้นถัดไปจนกว่าจะมีหลักฐานนั้น ถ้าผ่าน gate ไม่ได้ ให้หยุดและบอกผู้ใช้ว่าเพราะอะไร ห้ามหาทางเลี่ยง ถ้า gate มีตัวเลือกให้ผู้ใช้เลือก ตัวเลือกแรกต้องเป็นไปตาม `references/style.md` ตัวเลือกที่ขัดกฎข้อใดต้องเขียนกำกับว่า `breaks rule N` พร้อมเหตุผล ถ้าผู้ใช้เลือกตัวนั้น รายงานต้องระบุไว้คู่กับ PIN(behavior)

`references/style.md` กำหนดว่าโค้ดที่ดีหน้าตาเป็นอย่างไร ต้องอ่านก่อนเขียนโค้ดทุกครั้ง ทุก mode

## Input

| Input | ความหมาย | ค่าเริ่มต้น |
|---|---|---|
| `mode` | `new` = เขียนโค้ดใหม่ตั้งแต่ศูนย์ · `refactor` = จัดโครงโค้ดเดิมใหม่ · `migrate` = ทำต่อจากรายงานของ refactor: ย้ายคนเรียกไปหา V2 แล้วลบโค้ดเดิม | **ต้องระบุ** ถ้าไม่ระบุให้ถาม |
| target | `new`: จะสร้างอะไร ที่ไหน · `refactor`: ไฟล์หรือโฟลเดอร์ · `migrate`: path ของรายงาน | ต้องระบุ |
| `apply` | `v2` = เขียนสำเนาใหม่ไว้ข้างโค้ดเดิม โดยไม่แตะโค้ดเดิม · `replace` = เขียนทับโค้ดเดิมหลังผู้ใช้อนุมัติ | `v2` |
| `out` | ที่วางโค้ดใหม่ | `v2`: ข้างต้นฉบับ ตั้งชื่อตามกฎ V2 ในขั้นที่ 2 · `replace`: ที่เดิมของต้นฉบับ |
| `work` | โฟลเดอร์เก็บหลักฐาน: แผนที่, scenario, ผลบันทึก, รายงาน | `docs/readable/<unit>/` |
| `layout`, `depth`, `style` | ดู `references/style.md` | `A`, `3`, `auto` |

## ขอบเขต

จัดโครงใหม่ได้เฉพาะ**โค้ดภายใน**: service, utility, เนื้อในของงาน background โค้ดที่ติดกับ framework (HTTP view และ controller, serializer และ schema, ORM model, routing, migration) อยู่นอก unit ห้ามจัดโครงใหม่ ชื่อที่โค้ดพวกนี้เรียกเข้ามาใน unit นับเป็น public surface

**unit** คือโค้ดของงานหนึ่งงาน: ฟังก์ชันที่ไปถึงได้จาก entrypoint ของงานนั้น และไม่มีที่อื่นใช้ helper ที่โค้ดนอก unit ใช้ด้วยนับเป็น**ปลายทาง** เหมือนการเรียก library และอาจกลายเป็น unit ของตัวเองทีหลัง

**public surface** คือทุกชื่อที่โค้ด production นอก unit import ไปใช้ ไม่นับ tests ชื่อระดับบนสุดที่ไม่ขึ้นต้นด้วย `_` แต่ไม่มีอะไรใน repository import อาจถูกเรียกจากนอก repository ได้ ให้ระบุชื่อเหล่านี้ที่ gate ของขั้น Map แล้วถาม ถ้าผู้ใช้ไม่รู้ ให้นับเป็น public

## Mode `refactor`

### 1. Map

รัน `python scripts/jump_depth.py <target> --root <import root> --usage <repo dir> --check` จะได้รายการ entrypoint, public surface, คนที่เรียกเข้ามา, สิ่งที่เรียกออกไป, helper ที่ใช้ร่วมกับนอก unit และโค้ดที่ลงทะเบียนตัวเองตอน import (decorator ของ task, signal receiver) สิ่งที่ `--check` รายงานคือสิ่งที่ผิดอยู่ตอนนี้ ให้คัดลงใน `map.md` พร้อมตัวเลข จากนั้นเขียนความหมาย 1 บรรทัดให้ทุกฟังก์ชันเอง เพราะ script ทำไม่ได้

**แก้เฉพาะสิ่งที่ผิด** ถ้าไม่มีเรื่องเล่าไหนลึกเกิน 1 ชั้น แปลว่าโค้ดอ่านจากบนลงล่างได้อยู่แล้ว ห้ามเขียนเรื่องเล่าใหม่ เสนอแค่การย้ายที่ `--check` ระบุ บวกสิ่งที่มันมองไม่เห็น (ก้อนโค้ดซ้ำ, รหัสที่เขียนเป็น literal, เงื่อนไขยาว: กฎข้อ 5 ถึง 7 ใน `references/style.md`) หรือเสนอให้หยุด

ถ้าเป้าหมายมีมากกว่า 1 งาน ให้แบ่งเป็นหลาย unit งานละ unit และให้แต่ละงานมีไฟล์ของตัวเอง (การจัดไฟล์ดูที่ `references/style.md`) งาน (task) คือขั้นหนึ่งของ flow ทางธุรกิจ เช่น การทำเอกสารร่าง หรือการออกเอกสารฉบับสุดท้าย งานหนึ่งเป็นเจ้าของตัวงานเอง และทุก entrypoint ที่มีหน้าที่แค่เริ่มหรือส่งขั้นนั้นเข้าคิว แม้คนเรียกจะอยู่ที่อื่น สิ่งที่ทีมทำเพื่อแก้ขั้นที่ค้าง (retry, unlock) รวมกันเป็นงานเดียว โค้ดที่รันคนละขั้นคือคนละงาน แม้หน้าตาจะคล้ายกัน ส่วนผลผลิตเดียวกันหลายแบบที่สร้างในขั้นเดียวกัน (ตามประเภท, ตามบริษัท) คืองานเดียวที่มี branch งานหนึ่งมีได้หลาย entrypoint และอยู่ไฟล์เดียวกัน เขียนแผนลงใน `map.md`: งาน → entrypoint → ไฟล์ แล้วเสนอ `apply` ของแต่ละ unit:
- `replace` เหมาะกับ unit เล็กที่มีคนเรียกไม่กี่จุด หรือ unit ที่มีโค้ดลงทะเบียนตัวเอง
- `v2` เหมาะกับ unit ที่มีคนเรียกเยอะ คนเรียกอยู่หลาย package หรือ flow ที่เสี่ยง (เงิน, เอกสารที่ส่งออกไปข้างนอก)

อ่านการตั้งค่า lint และ CI ของโปรเจกต์ (เช่น ruff, pylint, flake8, Sonar, eslint, golangci-lint) แล้วเขียนลง `map.md` ทุกเพดานที่โปรเจกต์ตั้งเองและบังคับจริง เรื่องขนาดฟังก์ชัน ความซับซ้อน หรือโค้ดซ้ำ ค่าเริ่มต้นของเครื่องมือที่โปรเจกต์ไม่เคยตั้งไม่นับเป็นเพดาน ถ้าเรื่องเล่าจะเกินเพดานที่บังคับ ห้ามแบ่งเรื่องเล่าหรือปิดเครื่องมือเอง ให้ถามที่ gate พร้อมทางเลือก 3 ทาง:
- ปิดการเช็กนั้นเฉพาะจุดนั้น พร้อมเหตุผล ถ้าโปรเจกต์ยอมให้ทำ
- แบ่งเรื่องเล่าเป็นฟังก์ชันรายขั้นที่เป็นปลายทาง การตัดสินใจบางส่วนจะย้ายเข้าไปอยู่ในขั้น และรายงานต้องบอกไว้
- ให้คนเป็นคนแก้การตั้งค่า

ถ้า class ที่อาจเป็น public ส่ง state ระหว่าง method ผ่าน `self` method ที่เป็น public เปลี่ยนไม่ได้ ข้อตรวจ state ผ่าน `self` จึงผ่านไม่ได้ตราบที่ class ยังเป็น public ให้บอกที่ gate แล้วให้ผู้ใช้เลือก ถ้าผู้ใช้ให้คงเป็น public รายงานต้องระบุว่าเป็นกฎที่ผู้ใช้เลือกให้ขัด

**Gate:** มี `<work>/map.md` แล้ว และผู้ใช้อนุมัติ unit, ไฟล์และ `apply` ของแต่ละ unit, ชื่อระดับบนสุดที่ไม่มีใคร import ตัวไหนเป็น public และวิธีรับมือเพดาน lint ที่บังคับ (ถ้ามี) แล้ว

### 2. Clone

- `v2`: คัดลอกต้นฉบับไปที่ของ V2 ติด `_v2` ครั้งเดียว ที่ชั้นนอกสุดของสิ่งที่คัดลอก: folder → `utils_v2/`, ไฟล์ → `doc_v2.py`, ไฟล์ที่กลายเป็นไฟล์งานหลายไฟล์ → package `doc_v2/`, ฟังก์ชันหรือ class → `build_preview_v2` ชื่อข้างในใช้ชื่อเดิม V2 ห้าม import อะไรจากโค้ดเดิม
- `replace`: คัดลอกต้นฉบับแบบตรงทุก byte ไปไว้ที่ `<work>/before/` เพิ่มอีกชุด แล้วบันทึก hash ไว้ ห้ามแก้สำเนานี้

**Gate:** สำเนา import ได้

### 3. บันทึก baseline

เขียน `<work>/scenarios.py` ให้ public entrypoint ทุกตัวมีอย่างน้อย 3 scenario: สำเร็จ, error ทางธุรกิจ และการเรียกออกไปข้างนอกที่ล้ม (timeout หรือได้ response ที่เป็น error) ทุกอย่างนอก unit เป็น stub: ไฟล์อื่นของโปรเจกต์, database, HTTP, ที่เก็บไฟล์, queue, เวลา, uuid, ค่าสุ่ม ที่รันของจริงได้มีแค่ standard library และโมดูลใน allow-list (คำนวณล้วน ไม่มี I/O) ห้ามต่อ service หรือ database จริง

stub ของฟังก์ชันคำนวณล้วน เช่นการจัดรูปแบบวันที่หรือตัวเลข ให้ใส่ `.pure()` เพราะโค้ดที่ rewrite อาจเรียกมันจำนวนครั้งไม่เท่าเดิม ซึ่งไม่ใช่พฤติกรรม

บันทึกต้นฉบับลง `<work>/recordings/original.json` บันทึกสำเนาที่ยังไม่ได้แก้ด้วย แล้วเทียบสองตัวนี้ วิธีใช้และรูปแบบ scenario: `python scripts/parity.py --help`

**Gate:** ผลเทียบของสำเนาว่าง ซึ่งพิสูจน์ว่า harness ใช้ได้ การเรียกออกไปข้างนอกทุกจุดในแผนที่มี scenario อย่างน้อย 1 ตัวที่ไปถึง หรือรายงานบอกว่าทำไมไปไม่ถึง `parity.py coverage` บอกได้ว่าจุดไหนยังไม่มี scenario ไปถึง

### 4. Rewrite แบบ stand-alone

จัดโครงสำเนาใหม่ตาม `references/style.md` และกับดักใน `references/<ภาษา>.md` จุดที่ยังสรุปตอนนี้ไม่ได้ให้ปักไว้:
- `PIN(integrate): <อะไร>` ต้องทำตอนโค้ดใหม่เข้าไปทำงานแทน เช่น import, ชื่อ task, path ใน test
- `PIN(behavior): <อะไร>` ของแปลกหรือบั๊กที่คงไว้ตามเดิม

เขียน PIN ด้วย comment ของภาษานั้น สะกดตามนี้ทุกตัว เพื่อให้ค้นเจอ

### 5. Verify

- บันทึกโค้ดที่ rewrite แล้วเทียบกับ `original.json` ถ้าโค้ดที่ rewrite แตกเป็นไฟล์งานหลายไฟล์ ให้ใส่แต่ละไฟล์เป็น `--unit` ของตัวเอง scenario ชุดเดิมจะหา entrypoint เจอในไฟล์ใหม่ **ผลเทียบต้องว่าง**
- รัน `python scripts/jump_depth.py <rewrite> --root <import root> --usage <repo dir> --check` ถ้าเป็น V2 ให้เพิ่ม `--forbid <old module> --public-from <old module>` เพราะยังไม่มีใคร import V2 ชื่อที่เป็น public จึงต้องนับจากโมดูลเดิม จะไม่ผ่านถ้าไม่ครบทุกข้อ: ความลึกของโค้ดใน unit ≤ 1, inheritance ของโปรเจกต์ ≤ 1, ไม่มี state ส่งข้าม method ผ่าน `self`, import ในฟังก์ชันทุกตัวมี comment บอกเหตุผล (คงไว้ได้เฉพาะตัวที่ตัด circular import), V2 ไม่ import อะไรจากโค้ดเดิม และการจัดไฟล์ถูกต้อง: ฟังก์ชันที่ถูกเรียกจากไฟล์ของตัวเองอยู่ใต้ผู้เรียกเพียงตัวเดียวของมันในไฟล์นั้นทันที หรืออยู่ท้ายไฟล์ถ้ามีผู้เรียกในไฟล์นั้นหลายตัว, ฟังก์ชันใน `shared.py` ไม่เรียกกันเอง และไม่มี `__init__.py` ที่มีโค้ดหรือ re-export ชื่อ (ไม่มี facade)
- public surface ชื่อและ signature เหมือนเดิม ยกเว้นที่ผู้ใช้อนุมัติให้ V2 เปลี่ยน (ดูกติกาของการ refactor)

**Gate:** ผ่านทุกข้อ การอ่านโค้ดไม่ใช่การตรวจสอบ ถ้าข้อไหนรันไม่ได้ ให้เขียนลงรายงานแล้วหยุด

### 6. Report

เขียน `<work>/report.md` (ดูหัวข้อรายงาน) ถ้าเขียนไม่ได้ (บางสภาพแวดล้อมไม่ให้ subagent เขียนรายงาน) ให้ใส่รายงานทั้งหมดในข้อความสุดท้าย และบอกว่าไม่ได้เขียนไฟล์ แล้วหยุดที่นี่ ขั้นต่อไปต้องให้ผู้ใช้ตัดสินใจ

### 7. Integrate (เฉพาะ `replace` และหลังผู้ใช้อนุมัติ)

เขียนโค้ดที่ rewrite ทับต้นฉบับ แล้วเคลียร์ `PIN(integrate)` ให้หมด จากนั้นตรวจอีกรอบ:
- บันทึกผลจากตำแหน่งต้นฉบับ แล้วเทียบกับผลบันทึกของ `before/`
- import ทุกโมดูล production ที่ import unit นี้
- รัน test เดิม รายงาน test ที่ล้ม ห้ามแก้ test ให้ผ่าน

**Gate:** ผลเทียบว่าง, ไม่เหลือ `PIN(integrate)` และรายงานกับ checklist อัปเดตแล้ว

## Mode `migrate`

1. อ่านรายงาน แล้วสร้าง checklist ใหม่ด้วย `python scripts/jump_depth.py --callers <old module> --usage <repo dir>`
2. ก่อนย้ายอะไร บันทึกผลของโค้ดเดิมและ V2 ใหม่แล้วเทียบกัน ถ้าต่างแปลว่ามีคนแก้โค้ดเดิมหลังสร้าง V2 ให้หยุดและรายงาน
3. ย้ายเฉพาะคนเรียกที่ผู้ใช้เลือก แก้แค่ import หรือจุดที่เรียก ไม่แก้อย่างอื่น แล้วเคลียร์ `PIN(integrate)` ที่เป็นของคนเรียกพวกนั้น
4. import โมดูลที่แก้ แล้วรัน test เดิม
5. เมื่อ checklist ว่างและผู้ใช้อนุมัติ: แปลงผลบันทึกเป็น regression test ของ V2 เอง ลบโค้ดเดิมและ test ที่ patch ของภายในของมัน แล้วรัน test

**Gate:** checklist ในรายงานอัปเดตแล้ว

## Mode `new`

1. **หาของที่ใช้ซ้ำได้** ค้น helper, client และค่าคงที่ที่ feature ต้องใช้ โค้ดที่ที่อื่นใช้อยู่นับเป็นปลายทาง: เรียกใช้ ห้ามคัดลอกมา ห้ามจัดโครงใหม่ระหว่างทำ feature
2. **โครง** เขียนแผนที่หัวไฟล์ และเขียน entrypoint แต่ละตัวเป็นหัวข้อขั้นตอนมีเลข ยังไม่ใส่เนื้อ 1 ไฟล์ต่อ 1 งาน (การจัดไฟล์ดูที่ `references/style.md`) โค้ดที่ติดกับ framework ต้องบาง และเรียกเรื่องเล่า
   **Gate:** ผู้ใช้อนุมัติโครง
3. **เติมเนื้อ** แต่ละขั้นตาม `references/style.md`
4. **Test** ตามวิธีปกติของโปรเจกต์ ถ้าเป็น Python จะบันทึกการเรียกออกไปข้างนอกด้วย `parity.py` แล้วใส่ในรายงานด้วยก็ได้ ผู้ใช้จะได้รีวิว payload
5. **Verify** ด้วย `jump_depth.py --check` ใช้เกณฑ์เดียวกับขั้นที่ 5 ของ refactor และรันด้วย `--similar <repo dir>` ด้วย helper ที่เขียนใหม่แล้วหน้าตาเหมือนของที่มีอยู่ ต้องเปลี่ยนไปใช้ของเดิม หรือรายงานบอกว่าต่างกันอย่างไร
6. **Report** จบด้วย checklist ของงานต่อสายที่เหลือ: route, settings และสิ่งที่คนเท่านั้นทำได้ เช่น migration

## กติกาของการ refactor

- **ห้ามเปลี่ยนพฤติกรรม แม้จะดูเป็นการปรับปรุง** เช่น `None` → `"-"`, ปิดไฟล์, แก้บั๊กที่ซ่อนอยู่, ลบ import ที่ดูเหมือนไม่ได้ใช้ ให้ปัก PIN แล้วรายงาน
- **ห้ามลบโค้ด แม้จะไม่มีใครเรียก หรือไม่มีผู้เรียกไหนไปถึง:** ทั้งฟังก์ชัน, parameter และ branch เพราะอาจถูกเรียกด้วยชื่อ (ชื่อ task, URL config, `getattr`, template) หรือจากนอก repository และ branch ที่วันนี้ไม่มีใครเข้า พรุ่งนี้อาจมี ตอน inline helper ให้ยก branch ไปด้วยทุกตัว: parameter ที่ไม่มีผู้เรียกส่งมา ให้กลายเป็นตัวแปร local ที่ตั้งค่าเป็นค่าเริ่มต้นของมัน แล้ววาง branch ไว้ใต้ตัวแปรนั้นทันที เช่น `cleanup = ()` แล้วตามด้วย `if cleanup:` ปัก `PIN(behavior): no caller found` แล้วระบุในรายงาน PIN ใช้แทนโค้ดไม่ได้: โค้ดที่ปักไว้ต้องยังอยู่ การรวมก้อนที่ซ้ำกันทั้งก้อนใน flow เดียว (เช่นค้นหาและเช็คแบบเดียวกันสองครั้งติดกันหลัง inline helper สองตัว) คือกฎข้อ 6 ใน `references/style.md` ไม่นับเป็นการลบ ให้ระบุทุกครั้งที่รวมไว้ในรายงาน
- **public surface คงเดิม:** ชื่อเดิม signature เดิม มีแค่ V2 ที่ต่างได้ และต้องเป็นฟังก์ชันที่ผู้ใช้อนุมัติเป็นรายตัว เมื่อนั้นรายงานต้องบอกว่าคนเรียกแต่ละจุดต้องแปลง argument อย่างไร และ scenario ต้องเรียก V2 ผ่านการแปลงแบบเดียวกัน output ห้ามต่างเด็ดขาด: ค่าที่ return, error ที่ raise และการเรียกออกไปข้างนอกทุกครั้งตามลำดับพร้อม payload
- **ไม่มี facade** เมื่อ unit แตกเป็นไฟล์งานหลายไฟล์ ชื่อแต่ละตัวย้ายไปอยู่ในไฟล์ของมัน และคนเรียก import จากไฟล์นั้นตรง ๆ การแก้ import พวกนี้เป็น `PIN(integrate)`: ถ้าเป็น `v2` ทำใน mode `migrate` ถ้าเป็น `replace` ทำในขั้นที่ 7
- **tests ไม่ใช่ public surface** test ที่ patch ของภายในจะพัง ให้ระบุไว้ แล้ว refactor ต่อ ห้ามคงโครงที่แตกเป็นชิ้นไว้เพื่อ test พวกนั้น
- **ชื่อต้องอยู่รอดหลัง inline** เป็นหัวข้อขั้นตอน หรือเป็นชื่อตัวแปรที่เก็บผลลัพธ์ (ดู `references/style.md`)
- **โค้ดที่ลงทะเบียนตัวเองต้องไม่ทำงานซ้ำ 2 ชุด** เช่น decorator ของ task, signal receiver, schedule ถ้าเป็น `v2` ให้ปัก PIN และวางแผนไว้ในรายงาน unit แบบนี้ควรใช้ `replace`

## รายงาน

`<work>/report.md` มี:

1. **แผนที่ entrypoint:** entrypoint → ขั้นตอนที่มีเลข → การเรียกออกไปข้างนอก → payload แต่ละตัวประกอบที่ไหน (`file:line`)
2. **แผนที่ฟังก์ชัน:** ชื่อเดิม → ตำแหน่งใหม่ (inline เข้าขั้นที่ N, รวมกับก้อนที่ซ้ำ, เก็บเป็นปลายทาง หรือทำเป็น private)
3. **ตัวเลขก่อน → หลัง:** จำนวนฟังก์ชัน, ความลึกสูงสุด, ฟังก์ชันที่คนอ่านอาจต้องเปิดดู, import ที่ซ่อนในฟังก์ชัน, inheritance ของโปรเจกต์, state ที่ส่งข้าม method
4. **Parity:** จำนวน scenario ต่อ entrypoint, ผลเทียบ, การเรียกออกที่ไม่มี scenario ไปถึง
5. **PIN(behavior):** บั๊ก, ของแปลก และโค้ดที่ไม่มีใครเรียก ที่คงไว้ตามเดิม และกฎที่ผู้ใช้เลือกให้ขัดที่ gate (`breaks rule N`)
6. **ส่วนที่ตรวจไม่ได้:** ทุกอย่างที่การตรวจครอบคลุมไม่ถึง
7. **Checklist** อยู่ท้ายสุดเสมอ ทุก mode ไม่ว่าใครเป็นคน migrate สร้างจากการสแกนโค้ด ห้ามติ๊กด้วยมือ
   - `v2`: คนเรียกที่ยังใช้โค้ดเดิม (`file:line`), `PIN(integrate)` ที่ค้าง, test ที่ต้องลบพร้อมโค้ดเดิม และคำสั่งถัดไป: `/readable mode=migrate <report>`
   - `replace`: test ที่ล้ม และ `PIN(behavior)` ที่รอตัดสินใจ
   - `new`: งานต่อสายที่เหลือ และสิ่งที่คนเท่านั้นทำได้

## ภาษาและเครื่องมือ

เวอร์ชัน 1.x รองรับ**เฉพาะ Python** สคริปต์ต้องใช้ Python 3.10 ขึ้นไป (ใช้แค่ standard library) และโค้ดเป้าหมายต้องเป็น Python 3 ถ้าเป้าหมายเป็นภาษาอื่น ให้หยุดที่ขั้น Map แล้วบอกผู้ใช้ว่าเวอร์ชันนี้ยังไม่รองรับ `parity.py` ยัง stub การเรียกแบบ `await` ไม่ได้ ถ้าโค้ดเรียกออกไปข้างนอกด้วย `await` (`async def`) ให้บอกที่ gate ของขั้น Map แล้วหยุด การเรียกด้วยชื่อตอนรัน (`getattr(obj, name)()`, dict ที่เก็บฟังก์ชัน) `jump_depth.py` มองไม่เห็น ให้เขียนลง `map.md` เอง ถ้าใน repository มีสำเนาของโค้ดที่กำลังศึกษาอยู่ ให้ข้ามด้วย `--exclude <folder>`

| ความคิด | ความจริง |
|---|---|
| "test patch ของภายในพวกนี้ไว้ ต้องเก็บไว้" | tests ไม่ใช่ public surface ให้ระบุไว้แล้วทำต่อ |
| "ตรวจด้วยการอ่านอย่างละเอียดแล้ว" | นั่นไม่ใช่การตรวจสอบ ให้รัน parity หรือรายงานว่ายังไม่ได้ตรวจ |
| "แก้เล็กน้อยระหว่างทาง" | นั่นคือการเปลี่ยนพฤติกรรม ให้ปัก PIN แล้วรายงาน |
| "ลบ import ที่ไม่ได้ใช้" | อาจเป็น public surface ให้เช็กการใช้งานก่อน |
| "ไม่มีใครส่ง argument นี้ ตัด branch ทิ้งแล้วปัก PIN ไว้ได้" | คง branch ไว้ โดยให้ argument เป็นตัวแปร local ที่ตั้งค่าเริ่มต้น PIN ใช้กำกับโค้ด ไม่ได้ใช้แทนโค้ด |
| "ให้ผู้ใช้เลือกเอง: ก๊อปก้อนนี้ไปทั้งสองเรื่องเล่า หรือทำเป็นปลายทางตัวเดียว" | เสนอทางที่ตรงกฎก่อน ตัวเลือกที่ขัดกฎต้องเขียนกำกับว่า `breaks rule N` |
| "entry point ทั้งสองทำขั้นเดียวกัน ทำเป็นเรื่องเล่ากลางตัวเดียวที่รับ account หรือ flag" | แต่ละ entry point เป็นเรื่องเล่าของตัวเอง เฉพาะก้อนที่ซ้ำทั้งก้อนเท่านั้นที่เป็นปลายทาง (กฎ 6) และฟังก์ชันที่รับ flag ให้ inline เข้าแต่ละผู้เรียก |
| "ผ่าน gate ไม่ได้ เสนอให้ทำต่อแบบไม่ผ่าน gate" | หยุดและบอกเหตุผล ห้ามเสนอทางเลี่ยง gate เช่นทำ V2 โดยไม่มี parity |
